## Fixes delivered

- **Idle retention (handoff F2):** added lock-safe purge methods and a lifespan
  cleanup task for merchant flows and operator sessions. Shutdown cancels and
  awaits the task. Non-positive retention and invalid cleanup intervals are
  rejected. Expired records are removed without incoming requests.
- **Terminal data:** clear authorization URL and QR on terminal transitions and
  status reads; clear the browser's old link/QR too. Non-completed terminal flows
  drop their phone immediately. Completed flows retain it only for the five-minute
  continuity-session opt-in window, bounded also by flow retention; idle cleanup
  enforces that deadline within its configured interval (30 seconds by default).
  Creating a trust session clears the phone immediately.
- **Order/session binding:** repeated session creation returns the existing binding
  instead of replacing it and resetting fulfillment state. Concurrent creation
  receives 409; expired phone retention receives 410. Transport errors become 503.
  This is process-local protection; a lost upstream session-creation response
  still needs upstream idempotency for an exactly-once guarantee across retries.
- **Browser recovery:** transient non-2xx HTTP responses now retry automatically.
  Missing/expired flow and authentication failures stop with an actionable message.
  Existing COMPLETED-without-receipt recovery remains intact.
- **Packaging:** a built wheel previously contained Python modules only. It now
  carries HTML/JavaScript, locales, policy, signed registry, capability manifest,
  and lab recordings. The capability manifest moved from `docs/` into `app/` so
  an installed package can read it without the source tree.
- **Setup:** bootstrap now creates the `.venv311` environment Make prefers and
  validates Python >=3.11 instead of silently installing into a different venv.
- **Test isolation:** merchant harness credentials are pinned before test collection,
  eliminating order-dependent failures between review and harness tests.
- **Documentation:** rebuilt the README around the product, local run, API contract,
  evidence, source distinctions, submission priorities, and troubleshooting.
  Refreshed the fixed evaluation report using current output.

The initial checkout already contained a relevance-aware ALLOW gate, Act IX,
console entry, and matching tests. Those changes were reviewed and retained.
They increase the fixed 13-case evaluation from 28 to 38 calls and reduce its
conservative authored-expectation disagreements from six to three. Policy weights
and fixture labels were not tuned by this review.

## Suggestions for MENA Ignite

The [official GSMA overview](https://www.gsma.com/solutions-and-impact/gsma-open-gateway/gsma_events/gsma-mena-ignite-open-gateway-hackathon/)
requires CAMARA network APIs and AI. HackerEarth's linked challenge page timed
out during this review, so detailed rubric/submission deadlines were not verified.
Do not infer those deadlines from the broader GSMA event window.

1. **Prove AI and NaC before expanding features.** Capture a bounded real model
   run and a fresh Nokia hosted-simulator run. Show actual selection sources,
   fallback/STOP behavior, and provider provenance. Synthetic subscriber answers
   from a hosted simulator still need a synthetic label.
2. **Present one complete merchant journey.** Lead with a legitimate SIM change,
   explain CHALLENGE, record the merchant's verification outcome, and show the
   order decision without rewriting the signed receipt.
3. **Make the tradeoff reviewable.** Use the current 38/78 call comparison with
   all three expectation disagreements disclosed. Neither this dataset nor the
   generated baseline establishes fraud accuracy, operator pricing, or ROI.
4. **Finish focused UI validation.** Verify keyboard activation, small-screen
   flow recovery, reduced motion, 200% zoom, and a complete reviewed Arabic/RTL
   journey. Do not equate draft dictionary coverage with Arabic readiness.
5. **Secure physical handset proof and a merchant evaluator.** Follow the existing
   handset runbook once operator prerequisites exist; then collect real outcomes
   before calibrating risk thresholds or making business-impact claims.

The single-process architecture, reference-harness scope, real operator consent,
model proof, and outcome calibration remain explicit limits. A successful local
suite does not close those external validation gates.
